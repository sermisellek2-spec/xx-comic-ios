# 禁漫天堂首次接入与单次验证设计

## 目标

第一阶段只恢复禁漫天堂的基础浏览能力：首次需要时完成一次 Cloudflare 验证，随后先展示真实漫画列表，再加载并展示分类类型与分类。验证凭证失效前，翻页、筛选、刷新、切换页面和重启 App 都不得主动重复验证。

本阶段不修改漫画详情、章节目录、正文图片和图片解扰逻辑。基础列表与分类经过真机验收后，再单独设计后续链路。

## 已验证事实

- `https://18comic.vip/albums?o=mr&page=1` 和 `https://18comic.vip/theme/` 当前都会先返回 `403`，响应包含 `cf-mitigated: challenge`。
- 在真实浏览器中完成首次验证后，列表页包含约 80 个有效 `/album/{id}` 漫画链接。
- 同一浏览器会话随后打开 `/theme/` 不再验证，页面包含 7 组 `ul.btnmg` 分类。
- 当前列表卡片仍使用 `/album/{id}/{slug}`、漫画封面和 `title`/`alt`；当前分类页仍使用 `div.row > h4 + ul.btn-toolbar.btnmg`。现有路由与解析方向没有失效。

因此，当前首要问题是 App 的验证状态、会话调度和错误处理，而不是重新猜测站点接口。

## 当前问题

1. `CloudflareWebViewSession` 将主文档的 `403 + cf-mitigated: challenge` 与 DOM 挑战标记合并判断。验证完成后，如果 WebView 没有产生一次可识别的新主文档导航，旧响应状态会继续把正常 DOM 判为挑战页。
2. 设置页的“验证”按钮通过 `client.latest(1)` 是否返回非空列表判断验证结果。验证、列表抓取和列表解析被混成一个动作，任何解析失败都会被误报为验证失败。
3. 分类与默认列表可以分别发起请求。虽然 WebView 请求最终被串行化，但没有一个明确的禁漫启动顺序，也没有共享的首轮完成状态。
4. 分类请求异常在 `loadSourceCategories()` 中被静默忽略，用户只会看到分类消失，无法区分网络、验证、页面或解析错误。
5. 验证 WebView 创建时固定为 `0.01` 透明度。需要用户手动操作 Cloudflare 控件时，真实页面不可见，也无法形成可靠的交互兜底。

## 方案选择

采用“修正现有会话 + 禁漫专属启动编排”。继续使用现有 `CloudflareWebViewSession`、Android `CookieManager` 和 `WebStorage`，不复制 Cookie，不增加依赖，也不另写一套重复的 WebView 会话。

禁漫天堂仍持有自己的唯一 `jmcomicBrowserSession`。共享会话只修复通用的挑战状态判断和验证页可见性；列表优先、分类随后、手动验证探测等业务规则只放在禁漫链路中，不改变其他站源解析逻辑。

## 会话状态

禁漫会话使用以下逻辑状态：

- `IDLE`：没有活动请求，Cookie 是否有效未知。
- `NAVIGATING`：正在加载目标页面，界面不显示验证层。
- `VERIFYING`：当前页面确认是 Cloudflare challenge，同一站源的后续请求等待，不得再次发起验证。
- `VERIFIED`：当前请求已经获得预期站点的真实 DOM。该状态是会话提示，CookieManager 中的实际 Cookie 才是跨进程凭证。
- `FAILED`：本次导航因网络、验证超时、异常跳转或页面不匹配失败；下一次由用户触发重试。

每个请求必须绑定独立的导航序号。HTTP 状态、challenge 响应头、页面 URL、DOM 标记和完成回调只能作用于同一导航序号，旧导航信息不得污染新页面。

## 挑战判定

1. 当前 DOM 出现 Cloudflare/Turnstile 标记时，页面处于挑战状态。
2. 当前导航首次收到 `403 + cf-mitigated: challenge` 时，可进入 `VERIFYING`。
3. 已处于 `VERIFYING` 后，只要当前 URL 回到预期 `18comic.vip` 路径、页面加载完成、挑战 DOM 标记消失，并出现目标页面哨兵，就必须接受真实 DOM；旧的 `403` 不得继续阻止完成。
4. 未进入验证流程且当前导航返回普通 `4xx/5xx` 时，按真实 HTTP 错误失败。
5. 页面跳转到其他域名或错误路径时失败，不把登录页、广告页或 Cloudflare 页面交给漫画解析器。

列表页哨兵使用有效的 `a[href*="/album/"] img`，分类页哨兵使用 `ul.btnmg a[href]`。哨兵只负责证明拿到真实业务页面，不替代完整解析。

## 首次进入流程

1. 用户在发现页选择禁漫天堂。
2. App 清空旧的禁漫列表 UI 状态，但不清理 Cookie。
3. 使用唯一 `jmcomicBrowserSession` 请求 `/albums?o=mr&page=1`。
4. Cookie 有效时直接获得列表 DOM，不显示验证层。
5. Cookie 无效时进入 `VERIFYING`。自动验证期间显示轻量“正在验证”；需要手动操作时显示完全可见、可点击的真实 WebView。
6. 验证完成后在同一个页面直接捕获列表 DOM，不再发送第二个 `fetch()` 或额外验证请求。
7. 先解析并渲染漫画列表。列表成功是第一阶段的第一个可见完成点。
8. 列表成功后，再通过同一会话请求 `/theme/`。
9. 解析并渲染 7 组分类类型与对应分类。
10. 分类失败时保留已经展示的列表，显示紧凑的分类加载失败入口；重试只重新请求分类，不清 Cookie、不主动验证。

禁漫请求保持单活动导航。分类、翻页、搜索或手动验证在已有请求执行时进入同一 FIFO 队列，不能覆盖活动请求，也不能同时展开多个验证层。

## 后续请求与凭证失效

- 翻页、筛选和刷新继续使用同一 WebView、同一 User-Agent 和 CookieManager。
- App 重启后创建新的 WebView 实例，但直接复用 CookieManager 已持久化的 Cookie；不做启动时预验证。
- 任意后续请求真正返回 challenge 时，当前会话从 `NAVIGATING` 回到 `VERIFYING`，只为这一轮失效重新验证一次。
- Cloudflare 签发的新 Cookie 由 CookieManager 自动替换旧值并 `flush()`。
- 用户执行 App 缓存清理时，禁漫 Cookie、WebStorage 和 WebView 页面缓存会被清除；下次访问按首次流程重新验证。

## 手动验证

设置页的禁漫“验证”按钮只执行会话探测：请求固定列表入口，并检查预期 URL、无 challenge DOM 和列表页哨兵。它不调用 `latest()`，不解析漫画卡片，也不触发分类加载。

- 凭证有效：轻提示“验证有效”。
- 需要验证：进入与发现页完全相同的单次验证流程。
- 验证完成：轻提示“验证完成”。
- VPN/网络失败：提示“连接失败，请检查 VPN”。
- 超时或页面异常：显示对应的简短原因，不自动循环重试。

## 验证界面

- 自动 challenge：全屏层显示轻量“正在验证”，但不重复弹出。
- 需要手动操作：WebView 透明度切换为 `1`，占满可用区域并允许点击；状态提示放在不遮挡验证控件的位置。
- 完成后显示一次“验证完成”，短暂停留后恢复后台尺寸和不可点击状态。
- 失败或用户离开页面时关闭验证层并结束当前请求，不能留下透明蒙层拦截 App 触摸。

## 错误分层

禁漫基础链路至少区分以下错误：

- `NETWORK_OR_VPN`：域名不可达、连接超时或 TLS 失败。
- `CHALLENGE_TIMEOUT`：Cloudflare 验证在限定时间内没有完成。
- `UNEXPECTED_PAGE`：最终域名或路径不符合本次请求。
- `PAGE_NOT_READY`：页面加载完成但缺少业务页面哨兵。
- `LIST_PARSE_EMPTY`：列表 DOM 有效，但没有解析出漫画卡片。
- `CATEGORY_PARSE_EMPTY`：分类 DOM 有效，但没有解析出分类组。

错误日志记录请求类型、目标路径、最终 URL、导航序号、HTTP 状态、是否进入过验证、DOM 哨兵结果和解析数量。日志不得记录 Cookie 值。

## 解析契约

第一阶段保留现有路由：

- 列表：`/albums?o=mr&page={page}`
- 分类入口：`/theme/`
- 分类结果：`/albums...` 或 `/search/photos...`

列表解析继续接受 `src`、`data-src` 和 `data-original`，漫画标题优先取 `title`，其次取 `alt`。分类解析继续只接收 `/albums` 与 `/search/photos`，忽略广告、登录、书库等非漫画导航。

使用本次真实页面结构提取最小 HTML fixture，覆盖 `_3x4` 封面 URL、带 slug 的详情链接、7 组分类和非漫画链接过滤。fixture 不保存广告内容和完整成人页面。

## 验证与验收

自动化验证包括：

- 状态机测试：旧 `403/challenge` 后出现正常 DOM 时必须完成，不能继续验证。
- 单次验证测试：多个等待请求只能产生一次 `VERIFYING`。
- 列表 fixture 测试：当前卡片结构能解析出漫画 ID、标题和封面。
- 分类 fixture 测试：解析出 7 组分类并过滤非目录链接。
- 启动顺序测试：列表成功回调先于分类请求，分类失败不清空列表。
- 手动验证测试：验证成功不依赖 `latest()` 解析结果。

真机验收步骤：

1. 开启 VPN，清除 App 缓存后首次进入禁漫天堂，最多出现一次验证。
2. 验证结束后先看到真实漫画列表，随后看到 7 组分类。
3. 切换分类、翻页和刷新均不再次验证。
4. 退出并重启 App 后直接加载列表，不再次验证。
5. 清理缓存或凭证自然失效后，只重新验证一次。
6. 关闭 VPN 时得到明确连接提示，不进入无限验证。

## 非目标

- 不在本阶段修改详情、目录、正文参数、图片下载或图片解扰。
- 不将 Cloudflare Cookie 写入 SharedPreferences、JSON 或日志。
- 不加入主动定时验证、后台预热或自动重试循环。
- 不重构其他站源，也不改变其他站源的分类和列表行为。
