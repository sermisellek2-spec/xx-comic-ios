# 禁漫天堂混合会话优化设计

## 目标

修正禁漫天堂第一阶段真机验收暴露的三个问题：验证交互过重、列表与详情加载缓慢、分类类型和分类无法展示。

本轮采用方案 A：Cloudflare 验证只由 WebView 处理，验证后的业务请求优先复用同一份 Cookie 走普通 HTTP。方案 C（研究站点未公开的数据接口）仅记为后续待办，本轮不实现。

## 当前根因

`JmComicSource` 对主站的每个请求都调用 `CloudflareWebViewSession.fetch()`。因此列表、分类、详情和章节都会重新导航完整网页，加载脚本、广告和图片，并等待页面完成。即使 Cloudflare Cookie 仍然有效，业务请求也没有回到轻量 HTTP 链路。

验证状态在识别 challenge 后 1.2 秒即展开全屏 WebView。自动验证尚有机会自行完成时，页面已经遮挡 App，交互显得过重。

分类解析器只接受固定的 `div.row > h4 + ul.btn-toolbar.btnmg` 结构。旧样本可以解析 7 组，但页面加载慢、广告资源拖延或外层结构轻微变化都可能造成分类请求失败或解析为 0 组。

## 会话架构

保留现有 `BrowserSession` 接口，不引入新依赖。`CloudflareWebViewSession.fetch(url)` 内部改为以下流程：

1. 读取 Android `CookieManager` 中属于目标 URL 的 Cookie。
2. 使用与验证 WebView 一致的 User-Agent，通过 `HttpURLConnection` 请求业务页面。
3. HTTP 2xx/3xx 且页面不是 Cloudflare challenge 时直接返回 HTML。
4. 只有响应明确为 Cloudflare challenge 时，才串行回退到现有 WebView 验证流程。
5. WebView 验证成功后刷新 Cookie，并返回当前业务页 HTML。
6. 后续列表、分类、详情和章节继续从第一步走 HTTP，直至 Cookie 失效。

同一会话仍保持单请求串行，避免两个请求同时发现 Cookie 失效并各自打开验证页。普通 HTTP 404、500、连接失败和解析失败不得伪装成验证，也不得自动循环重试。

`CookieManager` 仍是凭证的唯一来源。设置页“清除缓存”继续清理 Cookie、WebStorage 和 WebView 缓存；清除后下次访问重新验证。App 重启但未清缓存时复用系统持久 Cookie。

## 轻量验证交互

首次命中 challenge 时通过现有蕾姆风轻提示显示“正在验证”，后台 WebView 保持隐藏，不立即遮挡当前页面。

自动验证等待时间由 1.2 秒调整为 4 秒。4 秒后 challenge 仍未完成，才展开可交互 WebView，让用户完成人机验证。验证成功后收起 WebView并显示一次“验证完成”。

轻提示和验证网页都不得重复创建。一次请求只允许出现一次“正在验证”和一次“验证完成”；Cookie 未失效时不得出现任何验证 UI。

## 分类解析

分类仍从 `/theme/` 获取，不硬编码 7 组静态数据，因为站点明确会动态调整分类。

解析以 `h4` 标题和其后最近的 `ul.btn-toolbar.btnmg` 为边界，不再依赖固定外层 `div.row`。每组只保留 `/search/photos` 和 `/albums` 业务链接，继续过滤广告、书库和外站链接。

分类请求失败时保留已经展示的漫画列表，显示现有轻量重试入口。解析为 0 组视为失败，不缓存空结果。

## 错误处理

- HTTP 明确返回 `403` 且带 `cf-mitigated: challenge`，或正文包含 Cloudflare challenge 标记：回退 WebView。
- HTTP 其他 4xx/5xx：直接报告站点 HTTP 错误，不打开验证页。
- HTTP 连接或读取超时：报告网络超时，不自动重试。
- WebView 验证超时：保留安全诊断信息，不记录 Cookie 或页面正文。
- 分类解析失败：仅标记分类失败，不清空漫画列表。

## 测试与验收

自动化测试覆盖：

- HTTP 正常页面不启动 WebView。
- Cloudflare challenge 才允许回退 WebView。
- 普通 403/500 不误触发验证。
- 分类在外层结构变化后仍能解析 7 组旧样本。
- 分类链接继续过滤广告和无关页面。
- 自动验证 4 秒前只产生轻提示，不展开交互页。

真机验收顺序：

1. VPN 开启并清理缓存，首次进入禁漫天堂。
2. 只出现一次轻量验证；自动验证无法完成时才展开网页。
3. 验证后列表先展示，分类随后展示。
4. 分类切换、翻页、刷新和进入详情均不再次验证，加载速度明显优于 1.0.32。
5. 重启 App 后继续复用有效 Cookie。
6. 清理缓存后凭证被清除，下次访问只重新验证一次。

## 后续待办：方案 C

在方案 A 稳定后单独抓取站点 XHR/fetch 流量，确认是否存在可长期使用的列表、分类、详情或章节内部接口。只有接口稳定、无需复制高频变化的签名算法，并且能够保留方案 A 作为降级路径时，才考虑逐项替换 HTML 请求。

本待办不包含在第一阶段，不阻塞方案 A 发布。
